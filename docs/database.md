# Database

This project uses **SQLite** via **SQLAlchemy** (through the
Flask-SQLAlchemy extension) — see [`architecture.md`](architecture.md) for
where the pieces live, and [`adding-models.md`](adding-models.md) for how to
add a table.

## Where the database file lives

- **Development:** `instance/app.db` — a real SQLite file, created
  automatically the first time `create_app()` runs. The `instance/` folder
  is gitignored; every developer gets their own local copy.
- **Testing:** `sqlite:///:memory:` — a fresh in-memory database per
  `create_app("testing")` call, never touches disk. See
  [`testing.md`](testing.md) for the isolation details/gotchas.
- **Production:** override `DATABASE_URL` in `.env` to point at a real
  database (e.g. Postgres) instead of SQLite. SQLite is fine for local dev,
  not for anything with concurrent writers.

## Inspecting the dev database

```bash
uv run flask shell
>>> from app.extensions import db
>>> from sqlalchemy import inspect
>>> inspect(db.engine).get_table_names()
```

Or just use the `sqlite3` CLI directly against `instance/app.db`.

## ⚠️ Schema changes go through migrations — `db.create_all()` won't save you

`db.create_all()` only creates tables that **don't already exist**. It will
never alter an existing table — add a column, rename one, change a type —
if the table is already there. Because of that, `create_app()` only calls
`db.create_all()` when `app.config["TESTING"]` is set (i.e., for the
in-memory test database, which is thrown away after every run and has no
migration history worth maintaining). **In development and production,
schema changes must go through Flask-Migrate/Alembic** — see the workflow
below.

If you forget this and just hand-edit a model, restart the app, and expect
the database to catch up — it won't. You'll get a confusing
`sqlite3.OperationalError: no such column` at runtime instead.

## Migration workflow (Flask-Migrate / Alembic)

Migrations already exist for this project (`migrations/`, tracked in git).
The commands below are what you run whenever you **add or change a model**:

```bash
# 1. Change/add a model in app/models/, and make sure it's imported
#    in app/models/__init__.py (see docs/adding-models.md).

# 2. Auto-generate a migration by diffing your models against the current
#    dev database schema:
uv run flask db migrate -m "Add <whatever> to <model>"

# 3. Read the generated file in migrations/versions/ — autogenerate is
#    good but not perfect (see caveats below), then apply it:
uv run flask db upgrade
```

Other commands you'll use:

```bash
uv run flask db current    # what migration is the dev db currently at?
uv run flask db history    # list all migrations
uv run flask db downgrade  # revert the most recent migration
```

**Commit the generated file in `migrations/versions/`** — migrations are
part of the codebase, not a local artifact. Every developer (and CI, and
production) applies the same migration history by running
`flask db upgrade`.

### Autogenerate caveats — always read the generated file

`flask db migrate` diffs your SQLAlchemy models against the live database
and writes a migration script for you, but it doesn't catch everything:

- **Data migrations** (backfilling a new non-nullable column, transforming
  existing values) are never autogenerated — you write those by hand in the
  generated file's `upgrade()`/`downgrade()` functions.
- **Renames** show up as a "drop column" + "add column" pair, which would
  silently drop existing data. If you renamed a column, edit the generated
  migration to use `op.alter_column(...)` instead.
- SQLite's limited `ALTER TABLE` support means Flask-Migrate/Alembic wraps
  changes in `with op.batch_alter_table(...)` — this is expected, don't
  remove it.

### First-time setup (already done for this repo)

For reference, this is how migrations were initialized — you shouldn't
need to repeat this, it's here so you understand where `migrations/` came
from:

```bash
uv run flask db init                          # created migrations/ (once, ever)
uv run flask db migrate -m "Add page model"   # generated the first migration
uv run flask db upgrade                        # applied it to instance/app.db
```

## Querying, the SQLAlchemy 2.0 way

Prefer the `select()`-style query API over the legacy `Query.filter_by()`
chaining style where practical:

```python
from sqlalchemy import select
from app.extensions import dbase
from app.models.post import Post

stmt = select(Post).where(Post.slug == "about")
page = dbase.session.scalars(stmt).first()
```

Both styles work with Flask-SQLAlchemy 3.x — the examples in
`adding-models.md` use the simpler `db.session.query(...)` form in a couple
of places for readability, but `select()` is the more modern/idiomatic form
worth knowing.
